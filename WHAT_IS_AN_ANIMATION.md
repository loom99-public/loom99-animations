# What Is An Animation?

This document captures our understanding of animation systems at a fundamental level, derived from analyzing the differences between HTML and React animation implementations and asking "what's the real root abstraction?"

## The Fundamental Definition

An animation is a **time-indexed program whose observable is a visual output**:

```
Animation = Behavior: (t, inputs) → state → pixels
```

Where "inputs" includes:
- User interaction (pointer, scroll)
- Prior state (for physics-based animations)
- Seeds (deterministic randomness)
- Layout/viewport
- Other running behaviors (for coordination)

## The Core Factorization

Animation systems keep rediscovering an old split from math/physics:

| Component | What it represents | Type signature |
|-----------|-------------------|----------------|
| **Curve** | "What happens" in state space, independent of when | `γ: [0,1] → S` |
| **Clock** | "When it happens", independent of what | `τ: ℝ → [0,1]` |
| **Render** | How state becomes pixels | `R: S → Pixels` |
| **Compose** | How multiple curves/schedules interact | `List<Anim> → Anim` |

The animation in time is their composition: `a(t) = γ(τ(t))`

### Why Clock and Curve Feel Related But Aren't

There's a group action of monotone reparameterizations on curves:
```
γ ↦ γ ∘ φ  where φ: [0,1] → [0,1]
```

If you allow "parameterization" to include these φ's, then clock and curve parameterization are both reparameterizations—one in normalized time, one in wall-clock time.

**Practical distinction:**
- **Clock** = globally shared "how time flows" (scrubbable timeline, spring integrator, reduced-motion preferences)
- **Parameterization** = per-element "how this thing responds to that clock"

They merge conceptually but separating them is useful because engineering constraints differ (scrubbing, determinism, accessibility, pausing, syncing).

## The Two-Stage Model

Most animation code gets messy because it mixes choosing motion family, sampling time, coordinating elements, and rendering. The fix: **compile a Plan once, then sample it many times**.

```
Compile stage (pure, deterministic):
  (Seed, Scene, Context) → Plan

Run stage (reactive sampling):
  (Plan, t, Inputs) → Frame
```

## The Missing Abstraction: Fields

The key insight from analyzing HTML vs React implementations: **initial conditions are generated by fields**.

```typescript
type Field<A> = (seed: Seed, n: number, ctx: CompileCtx) => A[]
```

- `Field<Point>` = origin field (where elements start)
- `Field<number>` = time-offset field (when elements start)
- `Field<any>` = per-element variation parameters

This is what was missing from the React implementation. The HTML "varied" animation has an implicit origin field generator; the React version hardcodes start positions per-line.

## Modes as Perceptual Equivalence Classes

### What Modes Are

A **mode** is a named `(originField, offsetField)` pair with a variance envelope:

```typescript
type Mode = {
  name: string;
  origin: Field<Point>;
  offset: Field<number>;
  envelope: {
    originRadius: number;   // spatial cohesion bound
    offsetJitter: number;   // temporal cohesion bound
  };
};
```

### Why Modes Exist

Modes exist because of **symmetries and equivalences**. The space of "all detailed animations" is rich, but the space of recognizable motion types is a **quotient**: you mod out by transformations that preserve perceived identity.

Transformations that don't change the "kind" of motion:
- Time shift (stagger): `t ↦ t - Δᵢ`
- Time scale: `t ↦ kt`
- Spatial symmetry: reflect/rotate/translate in state space
- Index permutation: relabel elements but preserve the gestalt

"Converge vs cascade vs diagonal" are **orbits under these transformations**. They name equivalence classes, not individual animations.

### Concrete Example: Converge Mode

```typescript
const converge: Mode = {
  name: 'converge',
  origin: (seed, n, ctx) => {
    const rng = createPRNG(seed);
    return Array(n).fill(null).map(() => ({
      x: rng.range(-150, -100),  // left of canvas
      y: rng.range(50, 150),     // middle-ish
    }));
  },
  offset: (seed, n, ctx) => {
    const rng = createPRNG(seed);
    const baseStagger = 80;
    return Array(n).fill(null).map((_, i) =>
      rng.vary(baseStagger * i, baseStagger * 0.2)
    );
  },
  envelope: {
    originRadius: 50,    // all origins within ~50px of each other
    offsetJitter: 16,    // stagger varies by ~16ms
  },
};
```

The three modes (converge/cascade/diagonal) are related by rotation/translation in origin space—orbits under SE(2) acting on the origin point.

## Phases as State Machines

Phases aren't just sequential animations—they're a **state machine with different rules per phase**:

```typescript
type Phase<S> = {
  name: string;
  duration: number;
  plan: (localT: Time) => Plan<S>;
};

type PhaseMachine<S> = {
  phases: Phase<S>[];
};
```

For the line drawing animation:
- **Entrance**: tail moves from origin to first point, body morphs from straight to curved
- **Hold**: everything frozen at final positions
- **Fold**: (optional) tail retracts, lines collapse

Each phase can have different clocks, different active elements, different rules.

## Constraints

Constraints are best modeled as: **the curve must end on a manifold**.

```typescript
type Constraint<S> = (s: S, ctx: CompileCtx) => S;

const constrainedCurve = <S>(curve: Curve<S>, project: Constraint<S>): Curve<S> =>
  (u) => u < 1 ? curve(u) : project(curve(1), ctx);
```

For the logo animation, the constraint is "end up forming readable text"—the final positions come from `LOGO_PATHS`.

## Identity and Continuity

"Line 0 is the same thing across frames" requires **stable identity before animation**:

```typescript
type SceneElement = {
  id: ElementId;           // stable across time
  final: Pose;             // target state
  correspondence?: Map;    // point-to-point mapping for morphs
};
```

Continuity is not emergent—it's an explicit input to compilation.

## Composition Algebra

Animation systems form something like a **monoidal category**:

| Operation | Meaning |
|-----------|---------|
| Sequential: `A ; B` | Do A then B |
| Parallel: `A ⊗ B` | Do A and B at once |
| Shift: `shift(A, Δ)` | Time-translate A by Δ |
| Stagger | Parallel + indexed time shifts |

Parallel composition needs a **merge operator** when animations affect the same property:
- Last-writer-wins
- Additive blending
- Weighted mixing
- Constraint solving

## The Truthy Checklist

When adding a feature, force it into one bucket:

| Bucket | What belongs |
|--------|--------------|
| **Field** | Compile-time variation, initial conditions |
| **Clock** | Time mapping, scrubbing, pausing, sync |
| **Curve** | What changes in state space |
| **Constraint** | What must be true (endpoints, bounds) |
| **Composition** | parallel/seq/shift/switch |
| **Render** | Projection to pixels |
| **Identity** | Correspondence, stable IDs |

If something doesn't fit cleanly, it's a smell that levels are being mixed.

## The State Space for Line Drawing

For shoot-in-and-curve animations:

```typescript
// What the behavior outputs (small, abstract)
type AnimState = {
  morphProgress: number;  // 0 = straight, 1 = curved
  opacity: number;
  strokeWidth: number;
  glowRadius: number;
  hueShift: number;
};

// What the renderer needs (compile-time context)
type RenderContext = {
  origin: Point;          // from Mode's origin field
  finalPoints: Point[];   // from scene definition
  baseColor: HSL;
};

// The path `d` string is derived:
// render(state, context) → SVGPathElement
```

The geometric interpolation (straight → curved) happens in the **renderer**, not the behavior. The behavior just outputs `morphProgress`.

## Why This Matters

The HTML and React implementations diverged because React didn't have:
1. **Origin fields** - start positions were hardcoded, not generated from modes
2. **Mode concept** - no named equivalence classes with variance envelopes
3. **Clean compile/run split** - curve generation mixed with rendering

With this framework:
- "Varied" becomes a mode with noise in its fields
- "Original" becomes a mode with zero variance
- New modes are just new field generators
- The same Plan can render to SVG, Canvas, or WebGL

## Implementation Path

1. PRNG with seed → deterministic randomness
2. Field generators → origins, offsets, per-element params
3. Mode definitions → named field bundles with envelopes
4. Plan compilers → `shootIn(scene, mode, seed) → Plan`
5. PhaseMachine → entrance/hold/fold orchestration
6. Renderer → `(Plan, t, input) → SVG mutations`
7. Driver → requestAnimationFrame or scrubber

This is the minimal system that expresses the deep structure without framework complexity.
