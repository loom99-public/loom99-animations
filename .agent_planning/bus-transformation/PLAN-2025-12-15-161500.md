## Executive Summary

Phase 1 is **COMPLETE** - all bus data model, store management, and routing interfaces are implemented. Phase 2 requires significant compiler architecture changes to support buses as first-class nodes in the compilation graph.

This sprint focuses on implementing a bus-aware compiler that:
- Builds dependency graphs including BusValue nodes
- Detects feedback loops with SCC validation
- Implements lazy Field evaluation with FieldExpr
- Supports multi-pass compilation with bus artifacts
- Provides deterministic ordering through sortKey

**Key Architecture Changes**:
1. **Bus-Aware Dependency Graph** - Nodes include BlockOut and BusValue types
2. **SCC Detection** - Tarjan's algorithm for feedback loop validation
3. **FieldExpr System** - Lazy field evaluation for efficient bus combination
4. **Multi-Pass Compilation** - Compile buses when visited, not at end
5. **Adapter Chain Support** - Automatic type conversion with validation

Total work items: 5 (P0: 4, P1: 1)

#### 2. SCC Detection and Feedback Loop Validation
**Status**: Not Started
**Effort**: Large (5-7 days)
**Dependencies**: Bus-aware dependency graph
**Spec Reference**: Feedback loop validation requirements
**Status Reference**: Current topological sort implementation

**Description**:
Implement Tarjan's algorithm for Strongly Connected Components detection to identify feedback loops. Add validation logic to allow only legal feedback loops that cross memory boundary blocks (DelayLine, Integrate, SampleHold).

**Acceptance Criteria**:
- [ ] Implement Tarjan's SCC algorithm:
  - tarjanS(graph): GraphNode[][] returns array of SCCs
  - Handles disconnected components gracefully
  - Provides deterministic component ordering
- [ ] Define memory block registry:
  - DelayLine, Integrate, SampleHold as memory blocks
  - Configurable block list for future memory types
- [ ] Implement validateFeedbackLoops(sccs, memoryBlocks):
  - Allow cycles only if they contain at least one memory block
  - Provide clear error messages for illegal cycles
  - Include cycle path in error for debugging
- [ ] Add cycle detection to compile pipeline:
  - Run SCC detection after graph construction
  - Fail compilation with clear errors for illegal cycles
  - Allow legal cycles to proceed to topological sort
- [ ] Test edge cases:
  - Self-loops (block output to its own input)
  - Multiple cycles in one patch
  - Nested cycles
  - Cycles spanning multiple lanes

**Technical Notes**:
- Tarjan's algorithm provides O(V+E) time complexity
- Memory blocks break causality and enable legal feedback
- Error messages must be user-friendly and actionable
- Consider performance for large patches (1000+ nodes)

#### 3. Multi-Pass Compilation with Bus Artifacts
**Status**: Not Started
**Effort**: Large (8-10 days)
**Dependencies**: SCC detection, FieldExpr types
**Spec Reference**: Multi-pass compilation process design
**Status Reference**: Current single-pass compilePatch function

**Description**:
Rewrite the compilation pipeline to handle buses as first-class nodes. This includes topological sorting with BusValue nodes, compiling buses when visited, and managing bus artifacts for listener resolution.

**Acceptance Criteria**:
- [ ] Extend topoSort to handle BusValue nodes:
  - topoSortBusAware(graph): GraphNode[] returns execution order
  - BusValue nodes appear after their publishers
  - BusValue nodes appear before their listeners
  - Maintains stable ordering with sortKey
- [ ] Implement compileBusValue(bus, publishers, artifacts):
  - Sort publishers by sortKey (deterministic ordering)
  - Apply adapter chains to publisher artifacts
  - Combine using bus.combineMode:
    - sum/average: numeric addition with weight support
    - max/min: comparison operation
    - last: use highest sortKey publisher
    - layer: specialized composition for visual types
  - Return single Artifact (FieldExpr or Program)
- [ ] Rewrite compilePatchBusAware(patch, registry):
  - Build dependency graph
  - Detect and validate cycles
  - Topological sort all nodes
  - Compile blocks and buses in execution order
  - Resolve listener inputs from bus artifacts
  - Return final RenderTreeProgram
- [ ] Add bus artifact tracking:
  - Map<string, Artifact> for bus values
  - Cache bus compilation results
  - Support bus re-compilation when publishers change

**Technical Notes**:
- Bus compilation is lazy - happens when node is visited
- sortKey ensures deterministic "last" and "layer" combine modes
- Adapter chains applied before combination, not after
- Error handling must identify problematic publishers

#### 4. FieldExpr Lazy Evaluation System
**Status**: Not Started
**Effort**: Large (6-8 days)
**Dependencies**: Multi-pass compilation foundation
**Spec Reference**: FieldExpr AST design and evaluation
**Status Reference**: Current bulk Field<T> implementation

**Description**:
Implement FieldExpr as an AST for lazy field evaluation. This enables efficient bus combination by creating expression trees that materialize only at final consumption, supporting fusion and optimization.

**Acceptance Criteria**:
- [ ] Define FieldExpr<T> AST types:
  - { kind: 'const'; value: T }
  - { kind: 'map'; src: FieldExpr<any>; fnId: string; params?: any }
  - { kind: 'zip'; a: FieldExpr<any>; b: FieldExpr<any>; fnId: string; params?: any }
  - { kind: 'source'; blockId: string; port: string }
  - { kind: 'bus'; busId: string; publishers: FieldExpr<any>[] }
  - { kind: 'adapter'; src: FieldExpr<any>; adapterId: string; params: any }
- [ ] Implement FieldExpr evaluator:
  - evaluateFieldExpr(expr, seed, n, ctx): readonly T[]
  - Handles all AST node types
  - Maintains evaluation order from dependencies
  - Provides memoization for repeated evaluation
- [ ] Add FieldExpr combinators:
  - mapFieldExpr(expr, fn, fnId): FieldExpr<B>
  - zipFieldExprs(a, b, fn, fnId): FieldExpr<C>
  - constFieldExpr(value): FieldExpr<T>
  - busFieldExpr(busId, publishers): FieldExpr<T>
- [ ] Update bus compilation to produce FieldExpr:
  - Field bus combination returns FieldExpr<Field<T>>
  - Signal bus combination returns FieldExpr<Signal<T>>
  - Combine modes create appropriate FieldExpr nodes
- [ ] Add optimization passes:
  - Constant folding for const nodes
  - Fusion of nested map operations
  - Dead code elimination for unused expressions

**Technical Notes**:
- FieldExpr enables zero-copy bus combination
- Materialization happens only at render time
- AST representation supports future optimizations
- Must integrate with existing bulk Field<T> at boundaries

- [ ] Create adapter chain builder:
  - findAdapterPath(from, to): AdapterStep[] (≤2 adapters max)

- [ ] Implement applyAdapterChain(artifact, chain, registry):
  - Sequentially apply adapters to transform artifact
  - Handle FieldExpr and Signal artifacts
  - Preserve metadata and optimization hints
  - Provide clear error messages for adapter failures
- [ ] Add adapter validation to bus routing:
  - Validate publisher→bus compatibility
  - Validate bus→listener compatibility
  - Show adapter chain in UI for transparency
  - Warn about heavy adapters (Reduce, Sample)

**Technical Notes**:
- Adapter chains limited to 2 adapters to prevent complexity
- Heavy adapters marked for user awareness
- Adapter discovery uses TypeDesc compatibility matrix
- Registry extensible for future adapter types

## Performance Considerations

### Targets
- Compilation time < 100ms for typical patches (50 blocks, 10 buses)
- FieldExpr evaluation overhead < 20% vs bulk Fields
- Memory usage < 2x current implementation

### Optimization Strategies
1. **Memoization**: Cache compiled bus artifacts
2. **Fusion**: Combine nested FieldExpr operations
3. **Incremental Recompilation**: Only recompile affected paths
4. **Lazy Evaluation**: Materialize fields only at consumption
