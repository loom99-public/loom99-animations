## Deliverable 1: Field Expression System with Domain-Aware Evaluation

**Priority**: P0 (Critical)
**Effort**: Large (1-2 weeks)
**Dependencies**: Phase 1 & 2 complete (UnifiedCompiler, TimeCtx, RuntimeAdapter)
**Spec Reference**: Architecture §G, §H (Fields, Element Identity) • **Status Reference**: STATUS-2025-01-18-164500.md §2 (Bus System - Missing Field compilation)

### Description

Implement the FieldExpr DAG system for lazy, domain-aware per-element value evaluation. This enables Field<T> buses to compile to expression trees that defer evaluation until sinks, avoiding unnecessary per-element closures and enabling zero-copy bus combination.

**Key architectural principle**: Fields compile to FieldExpr DAGs, not buffers. Evaluation is batched at sinks with explicit domain parameterization.

This involves:
1. Completing the FieldExpr type definitions (partially defined in `compiler/types-bus.ts`)
2. Implementing FieldExpr evaluator with element identity (elementId, TimeCtx, EvalCtx) → Value
3. Creating domain-aware batch evaluation at Field sinks
4. Implementing Field bus compilation in UnifiedCompiler (currently only Signal buses compile)
5. Adding FieldExpr combinators (map, zip, adapter chains)
6. Creating FieldExprCtx with memoization for repeated evaluation
7. Enforcing domain mismatch detection at compile time

### Acceptance Criteria

- [ ] FieldExpr type system complete with all node kinds (const, map, zip, source, bus, adapter)
- [ ] FieldExpr evaluator signature: `(elementId: string, timeCtx: TimeCtx, evalCtx: FieldExprCtx) → T`
- [ ] Domain type defined with stable element IDs, ordering, optional topology
- [ ] Domain mismatch detection produces compile-time errors (not runtime failures)
- [ ] Field buses compile to FieldExpr nodes (not just Signal evaluators)
- [ ] FieldExpr batch evaluator processes dense arrays at sinks (no per-element closures)
- [ ] Memoization cache in FieldExprCtx prevents redundant evaluation per frame
- [ ] FieldExpr combinators (map, zip) compose correctly without evaluating eagerly
- [ ] Adapter chains apply to FieldExpr nodes during bus compilation
- [ ] Element identity stability guaranteed across frames (no flicker)
- [ ] Per-element phase offsets work correctly with domain parameterization
- [ ] Test coverage: 20+ tests for FieldExpr evaluation, domain validation, bus compilation

### Technical Notes

**Domain Definition**:
```typescript
interface Domain {
  readonly id: string;              // Unique domain identifier
  readonly elements: readonly ElementId[];  // Stable element IDs
  readonly topology?: Topology;     // Optional neighbor relationships
}

type ElementId = string;  // Stable across frames
```

**FieldExpr Evaluation Strategy**:
- Evaluate at **sinks only** (blocks that consume Field values)
- Batch evaluation: iterate domain once, evaluate expression tree for each element
- Memoize per frame: cache FieldExpr results to avoid redundant computation
- No hidden iteration in FieldExpr nodes (no .map/.filter on arrays inside expressions)

**Bus Compilation for Field Buses**:
1. Collect all publishers to Field bus
2. Sort by sortKey, then stable ID
3. Apply adapter chains (producing new FieldExpr nodes)
4. Combine using domain-specific reducer (sum/average/max/min/last/layer)
5. Produce single FieldExpr node representing combined bus value

**Integration Points**:
- UnifiedCompiler must detect Field-world buses and route to FieldExpr compilation
- RuntimeAdapter must provide FieldExprCtx during evaluation
- Blocks consuming Field buses must trigger batch evaluation at their input ports

## Deliverable 2: Initial Block Migration (Scene + Phase Blocks)

**Priority**: P1 (High)
**Effort**: Medium (3-5 days)
**Dependencies**: Deliverable 1 (FieldExpr system), Phase 1 & 2 (UnifiedCompiler, TimeCtx)
**Spec Reference**: FULL_SYSTEM_SPEC.md §Phase 3 (Block Migration checklist) • **Status Reference**: STATUS-2025-01-18-164500.md §3 (Legacy compiler to remove)

### Description

Migrate the first set of critical blocks from the legacy `gallery/src/editor/blocks/` system to the unified compiler architecture. Start with Scene and Phase blocks as they are foundational for all animations and have clear Time/Field separation.

**Migration Strategy**: Implement from architectural principles, not copy-paste. Read the block's specification, ensure TimeCtx propagation, validate no implicit state.

Blocks to migrate:
- **Scene Blocks** (2): RadialOrigin, FlowFieldOrigin
- **Phase Blocks** (2): PhaseMachine, LinearPhase

These 4 blocks represent core primitives that enable most animations and test both Signal and Field worlds.

### Acceptance Criteria

- [ ] RadialOrigin block implemented in unified compiler

  - [ ] Tests: smoke test, domain validation, parameter variation

  - [ ] Outputs Field<Point> for flow field positions

  - [ ] Tests: smoke test, phase transitions, scrubbing behavior

- [ ] Legacy block definitions remain (not deleted yet - only delete when all blocks migrated)
- [ ] FULL_SYSTEM_SPEC.md updated with migration status checkmarks
- [ ] Integration test: Patch using all 4 blocks compiles and evaluates correctly

### Technical Notes

**Migration Pattern**:
```typescript
// Unified compiler block structure
export const RadialOriginBlock: BlockDefinition = {
  id: 'RadialOrigin',
  type: 'scene',
  inputs: {},
  outputs: {
    origin: { type: 'Field<Point>', world: 'Field', domain: 'Core' }
  },
  params: {
    centerX: { type: 'number', default: 0 },
    centerY: { type: 'number', default: 0 },
    radius: { type: 'number', default: 100 },
    angleOffset: { type: 'number', default: 0 }
  },
  compile: (instance: BlockInstance, inputs: CompiledInputs): CompiledBlock => {
    // Return FieldExpr node, not evaluated array
    return {
      id: instance.id,
      type: instance.type,
      evaluator: (inputVals, state, ctx) => {
        const fieldExpr: FieldExpr<Point> = {
          kind: 'map',
          src: { kind: 'domain', domainId: instance.params.domain as string },
          fnId: 'radialPosition',
          params: {
            centerX: instance.params.centerX,
            centerY: instance.params.centerY,
            radius: instance.params.radius,
            angleOffset: instance.params.angleOffset
          }
        };
        return { origin: fieldExpr };
      },
      requiresState: false,
      inputs: [],
      outputs: ['origin']
    };
  }
};
```

**Signal vs Field World**:
- **Signal blocks** (PhaseMachine, LinearPhase): Output `Signal<T>`, evaluated once per frame
- **Field blocks** (RadialOrigin, FlowFieldOrigin): Output `Field<T>`, lazy FieldExpr nodes

**TimeCtx Usage**:
- All temporal behavior reads from `ctx.t`, `ctx.dt`, `ctx.frame`
- No closures capturing time
- No calls to `Date.now()` or `performance.now()`

## Deliverable 3: Bus Signal Evaluator Compilation (Signal-World Only)

**Priority**: P2 (Medium) - **DEFERRED IF TIME CONSTRAINT**
**Effort**: Small (1-2 days)
**Dependencies**: Phase 1 & 2 (UnifiedCompiler, RuntimeAdapter)
**Spec Reference**: Architecture §F, §F1 (Bus Compilation Contract) • **Status Reference**: STATUS-2025-01-18-164500.md §2 (Bus system not integrated with compiler)

### Description

Complete the Signal bus compilation path in UnifiedCompiler to generate runtime Signal evaluators. This enables Signal-world buses (time, phase, control signals) to function end-to-end.

**Note**: This is separate from Field bus compilation (Deliverable 1). Signal buses are simpler: single value per frame, no domain awareness needed.

This involves:
1. Implementing Signal bus compilation in UnifiedCompiler
2. Generating Signal evaluator from publishers with combine mode
3. Integrating Signal bus evaluators into RuntimeAdapter evaluation loop
4. Supporting all combine modes (sum, average, max, min, last, layer)
5. Ensuring deterministic publisher ordering via sortKey

### Acceptance Criteria

- [ ] UnifiedCompiler detects Signal-world buses and routes to Signal compilation
- [ ] Signal bus compilation collects publishers sorted by sortKey
- [ ] Adapter chains apply correctly to Signal publishers
- [ ] Combine modes (sum, average, max, min, last, layer) generate correct evaluators
- [ ] Signal bus evaluators called during RuntimeAdapter evaluation loop
- [ ] Bus listeners receive Signal bus values as inputs to their blocks
- [ ] Deterministic: same patch produces same evaluation order across compilations
- [ ] Test coverage: 10+ tests for Signal bus compilation and combine modes
- [ ] Integration test: Patch with Signal bus (multiple publishers, one listener) evaluates correctly

### Technical Notes

**Signal Bus Evaluator Signature**:
```typescript
type SignalEvaluator = (timeCtx: TimeCtx, evalCtx: EvalCtx) => T
```

**Combine Mode Implementation**:
```typescript
function compileSignalBus(bus: BusDef, publishers: CompiledPublisher[]): SignalEvaluator {
  switch (bus.combineMode) {
    case 'sum':
      return (timeCtx, evalCtx) => {
        let sum = 0;
        for (const pub of publishers) {
          sum += pub.evaluate(timeCtx, evalCtx);
        }
        return sum;
      };
    case 'average':
      // ...similar pattern
    case 'last':
      return (timeCtx, evalCtx) => publishers[publishers.length - 1].evaluate(timeCtx, evalCtx);
    // etc.
  }
}
```

**Integration with RuntimeAdapter**:
- After evaluating all blocks in dependency order, evaluate all bus signals
- Store bus signal results in EvalCtx for listener access
- Listeners read from EvalCtx when their inputs reference buses

## Risks and Mitigations

### High Risk Areas

1. **FieldExpr Performance** - Lazy evaluation overhead
   - *Mitigation*: Benchmark against eager evaluation baseline
   - *Mitigation*: Implement memoization cache to avoid redundant computation
   - *Mitigation*: Profile hot paths and optimize expression tree traversal
   - *Target*: <5% overhead vs direct array access

2. **Domain Mismatch Detection** - Runtime errors instead of compile-time
   - *Mitigation*: Validate domain compatibility during bus compilation
   - *Mitigation*: Type-level domain tracking in FieldExpr nodes
   - *Mitigation*: Comprehensive domain validation tests
   - *Target*: Zero runtime domain errors with good compile-time errors

3. **Block Migration Incompleteness** - Migrated blocks missing features
   - *Mitigation*: Start with simplest blocks (Scene, Phase) before complex ones
   - *Mitigation*: Compare outputs with legacy blocks during testing
   - *Mitigation*: Keep legacy blocks until all tests pass with unified versions
   - *Target*: 100% feature parity for migrated blocks

### Medium Risk Areas

4. **Test Coverage Gaps** - Missing edge cases in FieldExpr evaluation
   - *Mitigation*: Property-based testing for FieldExpr combinators
   - *Mitigation*: Integration tests with realistic patch configurations
   - *Target*: 85%+ coverage for FieldExpr, 100% for blocks

5. **Documentation Drift** - Architecture docs not updated with FieldExpr details
   - *Mitigation*: Update architecture doc with FieldExpr section during implementation
   - *Mitigation*: Add inline JSDoc for all FieldExpr types and functions
   - *Target*: Zero doc debt at sprint end
