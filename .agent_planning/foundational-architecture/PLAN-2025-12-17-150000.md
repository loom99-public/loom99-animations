## Deliverable 1: Unified Time Model and TimeCtx Implementation

**Priority**: P0 (Critical)
**Effort**: Large (1-2 weeks)
**Dependencies**: None

### Description
Implement the unified TimeCtx structure that will serve as the single time source throughout the system. This addresses the most critical architectural gap where the system currently has three different time representations (V4 Signal, Player/Program, and specification).

This involves:
1. Defining the TimeCtx type with t, dt, frame, and mode
2. Creating TimeCtx factory functions for scrub and performance modes
3. Migrating V4 Signal evaluation to use TimeCtx
4. Updating Player/Program to generate and use TimeCtx
5. Adding TimeCtx propagation throughout the evaluation pipeline

### Acceptance Criteria
- [ ] TimeCtx type defined with all required fields (t, dt, frame, mode)
- [ ] TimeCtx factories create appropriate contexts for scrub vs performance modes
- [ ] V4 Signal<A> type updated to `(timeCtx: TimeCtx, evalCtx: EvalCtx) => A`
- [ ] All existing V4 animations compile and run with new TimeCtx signature
- [ ] Player/Program updated to generate TimeCtx for each frame
- [ ] TimeCtx propagation implemented in compiler pipeline
- [ ] Migration compatibility layer ensures no breaking changes to existing animations
- [ ] Performance tests show <5% overhead from TimeCtx propagation

### Technical Notes
- Must maintain backward compatibility with existing V4 animations
- Consider using a migration adapter pattern to minimize breaking changes
- TimeCtx should be immutable to prevent accidental mutation
- Mode field will enable future scrub vs performance optimizations
- Frame counter essential for stateful blocks and deterministic behavior

## Deliverable 2: Context Separation and Type Clarification

**Priority**: P0 (Critical)
**Effort**: Medium (3-5 days)
**Dependencies**: None (can be done in parallel with Deliverable 1)

### Description
Clarify and implement the separation between EvalCtx, CompileCtx, and RuntimeCtx throughout the compilation and evaluation pipeline. This resolves the ambiguity identified in the evaluation where these concepts are mixed.

This involves:
1. Defining clear interfaces for each context type
2. Mapping current Context usage to appropriate context types
3. Implementing context transformation logic between compilation phases
4. Updating compiler pipeline to use correct context types
5. Adding validation to ensure context boundaries are respected

### Acceptance Criteria
- [ ] EvalCtx interface defined for signal evaluation (environment + inputs)
- [ ] CompileCtx interface defined for compilation-time operations
- [ ] RuntimeCtx interface defined for runtime state management
- [ ] All compiler phases use appropriate context types
- [ ] Context transformation functions implemented between phases
- [ ] Validation errors thrown when context boundaries are violated
- [ ] Type safety ensures compile-time detection of context misuse
- [ ] Documentation shows clear mapping between old and new context usage

### Technical Notes
- EvalCtx should be focused and minimal (only what signals need)
- CompileCtx contains compilation-specific data like dependency graphs
- RuntimeCtx manages mutable state and execution context
- Consider using branded types to prevent context confusion
- Migration strategy should allow gradual adoption

## Deliverable 3: Explicit State Block Interface Design

**Priority**: P1 (High)
**Effort**: Medium (3-5 days)
**Dependencies**: Deliverable 1 (TimeCtx), Deliverable 2 (Context Separation)

### Description
Design and implement the interface for explicit state blocks that allows blocks to declare their memory shape and scrub behavior. This enables stateful phase clocks and user-defined state while maintaining the architecture's explicit state principle.

This involves:
1. Defining StateShape interface for describing block memory
2. Creating ScrubPolicy enum and interface for behavior declaration
3. Implementing StateBlock interface that extends regular Block
4. Adding state block registration mechanism
5. Creating framework for stateful evaluation with proper lifecycle
6. Implementing initial state block types (Delay, Integrate, History)

### Acceptance Criteria
- [ ] StateShape interface defined for describing memory layout
- [ ] ScrubPolicy interface defined with all scrub behavior options
- [ ] StateBlock interface extends Block with state-specific properties
- [ ] State block registration system implemented in block registry
- [ ] Delay block implemented with configurable delay and scrub policy
- [ ] Integrate block implemented with accumulation and reset behavior
- [ ] History block implemented with configurable buffer size
- [ ] State blocks integrate properly with compiler pipeline
- [ ] State serialization/deserialization works for save/load
- [ ] Scrub behavior respects declared policies for deterministic behavior

### Technical Notes
- StateShape should be type-safe and serializable
- ScrubPolicy options: hold, reset, interpolate, recompute
- State blocks must declare dependencies for proper compilation order
- Consider using immutable state snapshots for scrub safety
- State initialization should be explicit and controllable
- Memory usage should be bounded and predictable
