# PhaseClock Redesign - Current Status

**Date**: 2024-12-19
**Reference**: `feature_planning_docs/TimeRoot/3-PlayerTimePhaseClockChanges.md`

---

## Current Implementation

**Location**: `gallery/src/editor/compiler/blocks/domain/PhaseClock.ts`

### Current Behavior
PhaseClock is a **time source** that generates phase directly from `tMs`:
- **No inputs** - it creates its own time progression
- Takes time directly from player (unbounded `tMs` parameter)
- **Wraps internally** based on mode (loop/once/pingpong)
- Single output: `phase: Signal<number>`
- Parameters: `duration`, `mode`, `offset`

### Current Port Structure
```typescript
inputs: []
outputs: [
  { name: 'phase', type: { kind: 'Signal:number' } }
]
```

### Current Semantics
```typescript
// Owns time, wraps it internally
const signal: SignalNumber = (tMs) => {
  const t = tMs + offsetMs;
  switch (mode) {
    case 'loop': return (t % durationMs) / durationMs;
    case 'once': return clamp(t / durationMs, 0, 1);
    case 'pingpong': // triangle wave
  }
};
```

**Key Problem**: PhaseClock competes with player for "who defines looping." This creates confusion:
- Is the patch looping because PhaseClock has `mode='loop'`?
- Or because player wraps time at maxTime?
- What if there are multiple PhaseClocks with different modes?

## Required Changes (Per Spec)

### 1. Port Changes - PhaseClock Becomes Derived

**New Inputs** (exactly one required):
- `tIn: Signal<time>` - unbounded time from TimeRoot (canonical)
- `phaseIn: Signal<phase>` - existing phase to transform (secondary)

**New Outputs** (expanded from current):
- `phase: Signal<phase>` - primary phase output [0,1] based on mode
- `u: Signal<unit>` - clamped [0,1] progress (for envelopes)
- `wrap: Signal<event>` - fires on cycle boundaries
- `cycleIndex: Signal<number>` - monotonic wrap counter

**New Configuration Inputs**:
- `period: Scalar<duration>` - replaces current `duration` param
- `mode: Scalar<string>` - 'loop' | 'pingpong' | 'once' (stays local)
- `rate: Signal<number>` - speed multiplier (optional, default 1.0)
- `phaseOffset: Signal<phase>` - offset after computation (optional, default 0)
- `reset: Signal<event>` - reset to phase=0 (optional, transport-only)

### 2. Semantic Changes

**Current**: PhaseClock is a **primary time source**
**New**: PhaseClock is a **derived clock / phase transformer**

The mode parameter is now **explicitly local** - it affects THIS clock's behavior, not patch topology.

Only `CycleTimeRoot` can define patch looping. PhaseClock may loop locally even in a finite/infinite patch.

### 3. Type System Changes

**Current**: Works with legacy `Signal:number` string types
**New**: Must use `TypeDesc` system with proper domains:

```typescript
// Input
tIn: { world: 'signal', domain: 'time' }
// OR
phaseIn: { world: 'signal', domain: 'phase' }

// Outputs
phase: { world: 'signal', domain: 'phase' }
u: { world: 'signal', domain: 'unit', semantics: 'progress' }
wrap: { world: 'special', domain: 'event', semantics: 'wrap' }
cycleIndex: { world: 'signal', domain: 'number', semantics: 'cycleIndex' }
```

### 4. Scrub Safety

PhaseClock must declare scrub-safety:
- If driven by scrub-safe TimeRoot → scrub-safe
- If using transport-only inputs (reset events) → transport-only

Need block-level capability flag (future, but design for it).

## Breaking Changes

### For Existing Patches
**Any patch using PhaseClock will break** because:
1. Current PhaseClock has no inputs, new one requires `tIn` or `phaseIn`
2. Output type changes from `Signal:number` to `Signal:phase` (with proper TypeDesc)
3. Param `duration` → `period` (semantic change, same meaning)

### Migration Strategy
**Option 1**: Create new block type `PhaseClockV2`, deprecate old one
**Option 2**: Auto-migrate on load (connect to implicit TimeRoot)
**Option 3**: Hard break, require manual rewiring

**Recommendation**: Option 2 with clear migration log.

### For Block Library
- Must have `TimeRoot` blocks available before PhaseClock can function
- UI should guide: "PhaseClock needs a time input. Add a TimeRoot?"

## Dependencies

### Hard Dependencies (must exist first)
1. **TimeRoot blocks** - PhaseClock needs `Signal<time>` input
   - `FiniteTimeRoot`, `CycleTimeRoot`, `InfiniteTimeRoot`
   - Currently being planned in parallel
2. **TypeDesc system** - must support `domain: 'time' | 'phase'`
   - Already exists in `types.ts`, but needs validation

### Soft Dependencies (nice to have)
- Event system for `wrap` output and `reset` input
- Bus system to publish `phase` / `u` / `wrap` to other blocks
- Scrub-safety infrastructure for capability flags

Keep `rate`, `phaseOffset`, `reset` as future (after core is stable).
