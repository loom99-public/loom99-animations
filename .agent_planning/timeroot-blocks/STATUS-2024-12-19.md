# TimeRoot Blocks - Current State Assessment

**Date**: 2024-12-19
**Topic**: timeroot-blocks
**Dependency**: timemodel-types (planned but not yet implemented)

## Reference Specification
`feature_planning_docs/TimeRoot/1-PlayerTimeConstraints.md`

## What Exists Today

### Current Time Blocks
- **PhaseMachine** (`blocks/legacy/time.ts`) - Three-phase animation (entrance/hold/exit)
  - Outputs: `Signal<PhaseSample>`
  - Parameters: entranceDuration, holdDuration, exitDuration
  - Implies finite time topology but not enforced

- **PhaseClock** (`blocks/legacy/time.ts` and `blocks/domain.ts`) - Time-based phase progression
  - Outputs: `Signal<number>` (phase value)
  - Modes: loop, once, pingpong
  - Parameters: duration, mode, offset
  - Implies cyclic time when mode='loop' but not enforced

### Current Compiler
- **compilePatch()** (`compiler/compile.ts`)
  - Returns: `CompileResult { ok, program?, errors, compiledPortMap? }`
  - No TimeModel in output type
  - No validation for TimeRoot blocks
  - No constraint checking for time topology

### Current Type System
- **TypeDesc** (`types.ts`) - Bus typing with world/domain/category
  - Supports Signal and Field worlds
  - Has 'time' and 'phase' as CoreDomains
  - No TimeModel or TimeRoot concepts

## What's Missing

### 1. TimeRoot Block Definitions
No blocks exist with the required TimeRoot semantics:
- ❌ FiniteTimeRoot(durationMs)
- ❌ CycleTimeRoot(periodMs, mode)
- ❌ InfiniteTimeRoot(windowMs)

### 2. Compiler Validation
No enforcement of time topology constraints:
- ❌ Exactly one TimeRoot per patch
- ❌ Detection of conflicting time blocks
- ❌ Validation that time-derived blocks connect to TimeRoot

### 3. Required Outputs
No standardized signal outputs per spec:
- ❌ `systemTime: Signal<time>` (always)
- ❌ `phaseA: Signal<phase>` (for CycleRoot)
- ❌ `progress: Signal<number>` (for FiniteRoot)
- ❌ `window: { startTime, endTime }` (for InfiniteRoot)

### 4. TimeModel Integration
- ❌ TimeModel types not in compiler types
- ❌ CompileResult doesn't include TimeModel
- ❌ No connection between TimeRoot blocks and TimeModel output

## Dependencies

### Must Complete First
**timemodel-types** sprint must be completed before implementing TimeRoot blocks:
- Need `TimeModel` union type defined
- Need `CompiledProgram { program, timeModel }` output type
- Need compiler infrastructure to output TimeModel

### Blocks on This
Cannot implement until timemodel-types is done:
- TimeRoot blocks need to declare which TimeModel they produce
- Compiler validation needs TimeModel types to check conflicts
- Required output signals depend on TimeModel kind

## Current Time Behavior

### Existing Patterns
1. **PhaseMachine patches** → Finite behavior (entrance/hold/exit)
   - Duration = entranceDuration + holdDuration + exitDuration
   - Naturally finite but not declared as such

2. **PhaseClock with mode='loop'** → Cyclic behavior
   - Wraps phase at period boundary
   - Naturally cyclic but not declared as such

3. **No explicit infinite patches** → Default behavior unclear

### Player Time Handling
- Player currently wraps time at maxTime (hardcoded or inferred)
- No concept of TimeModel in player
- Time topology is implicit, not explicit

## Risks

### Migration Challenges
- Existing patches have implicit time topology
- Adding "exactly one TimeRoot required" will break existing patches
- Need migration path or backward compatibility strategy

### Block Relationships
- PhaseMachine and PhaseClock overlap with TimeRoot semantics
- Need to clarify: Are these time-derived blocks or do they define topology?
- Spec says "time-derived blocks cannot exist floating" - enforcement needed

## Next Steps (Post-Dependency)

Once timemodel-types is complete:
1. Define three TimeRoot block types
2. Add compiler validation for exactly-one constraint
3. Define required output ports per TimeRoot type
4. Create migration strategy for existing patches
