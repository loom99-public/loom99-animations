## Deliverable 2: Implement New PhaseClock (Core Variant)

### Must-Have Criteria

#### Block Definition
- [ ] New `PhaseClock` block defined in `blocks/domain.ts`
- [ ] Inputs: `tIn` with type `Signal<time>` (or compatible string notation)
- [ ] Outputs: `phase` (Signal<phase>), `u` (Signal<unit>)
- [ ] Params: `period` (number, default 3.0), `mode` (select: loop/once/pingpong)
- [ ] Block metadata: correct label, description, color, category

#### Compiler Implementation
- [ ] Compiler file: `compiler/blocks/domain/PhaseClock.ts`
- [ ] Validates `tIn` input is connected (throws clear error if missing)
- [ ] Validates `period > 0` (throws clear error if invalid)
- [ ] Validates `tIn` has correct type (throws if mismatched)
- [ ] Computes `phase` correctly for all three modes:
  - **loop**: `phase = (t / period) % 1` (handles negatives correctly)
  - **once**: `phase = clamp(t / period, 0, 1)`
  - **pingpong**: `phase` oscillates 0→1→0 in triangle wave
- [ ] Computes `u` correctly for all modes:
  - Always in [0,1] range
  - For pingpong: tracks forward/backward progress appropriately

#### Type System Integration
- [ ] Port definitions use TypeDesc or compatible string notation
- [ ] `portUtils.ts` recognizes `domain: 'time'` and `domain: 'phase'`
- [ ] Type checking allows connecting time sources to `tIn`
- [ ] Type checking prevents incompatible connections

#### Block Registry
- [ ] New block exported from `compiler/blocks/domain/index.ts`
- [ ] Block registered in compiler's block map
- [ ] Both legacy and new blocks coexist without conflicts

### Verification Steps

1. **Manual wiring test**:
   - Open editor
   - Add `InfiniteTimeRoot` block (or time source)
   - Add new `PhaseClock` block
   - Wire `InfiniteTimeRoot.t` → `PhaseClock.tIn`
   - Set period = 2.0, mode = loop
   - Add block that consumes phase output
   - **Verify**: Compiles without errors

2. **Loop mode behavior**:
   - Create patch: TimeRoot → PhaseClock(mode=loop, period=2.0) → output
   - Sample phase at t = [0, 1000, 2000, 3000, 4000] ms
   - **Expected**: [0.0, 0.5, 0.0, 0.5, 0.0]

3. **Once mode behavior**:
   - Create patch: TimeRoot → PhaseClock(mode=once, period=2.0) → output
   - Sample phase at t = [0, 1000, 2000, 3000] ms
   - **Expected**: [0.0, 0.5, 1.0, 1.0]

4. **Pingpong mode behavior**:
   - Create patch: TimeRoot → PhaseClock(mode=pingpong, period=2.0) → output
   - Sample phase at t = [0, 1000, 2000, 3000, 4000] ms
   - **Expected**: [0.0, 0.5, 1.0, 0.5, 0.0]

5. **u output correctness**:
   - For each mode above, verify `u` output is in [0,1]
   - **Expected**: u never exceeds 1.0 or goes below 0.0

6. **Error handling**:
   - Try to compile PhaseClock with no `tIn` connected
   - **Expected**: Clear error message "PhaseClock: tIn input required"
   - Set period = 0 or negative
   - **Expected**: Clear error message "PhaseClock: period must be > 0"

## Rollback Criteria

If any of these occur, consider rolling back the sprint:

1. **Breaking change**: Existing patches fail to load or run
2. **Type system conflict**: New TypeDesc breaks port connections
3. **Test failures**: Cannot achieve >95% test pass rate
4. **Performance regression**: Compilation or runtime significantly slower
5. **Semantic errors**: Phase computation fundamentally incorrect per spec

**Rollback procedure**:
1. Revert all commits from this sprint
2. Document blockers in STATUS.md
3. Re-plan with smaller scope or different approach
