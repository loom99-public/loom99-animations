## 1. Design Decisions (BLOCKING - Must Resolve First)

### P0: Connection UI Design & Interaction

**Status**: Not Started
**Complexity**: Medium (design decision, not implementation)
**Dependencies**: None
**Spec Reference**: ui_specifics.md § "Unified Editor" § Layout
**Status Reference**: STATUS-2025-12-12-180205.md § Ambiguities § Question 1

#### Description

Users need to wire blocks together (output slot → input slot) to build animations. The connection creation interaction and visual rendering approach must be chosen before Phase 3 implementation begins.

**Evidence from STATUS**: Current store has `connect(from, to)` method and connection data structure, but no UI calls it. Connection visualization missing entirely.

#### Analysis & Recommendation

**Option A: SVG Lines (Node Editor Pattern)**
- Visual: Bezier curves connecting block slots
- Interaction: Drag from output slot, drop on input slot
- Examples: Unreal Blueprint, Blender Shader Editor, Houdini
- **Pros**: Intuitive, shows data flow clearly, familiar to technical users
- **Cons**: Complex implementation (curved line math, collision detection, drag-to-reroute)
- **Effort**: Large (3-5 days - line rendering, collision, rerouting)

**Option B: Click-to-Connect**
- Visual: SVG lines appear after connection made
- Interaction: Click output slot (highlights valid inputs), click input slot (connects)
- Examples: Some MIDI editors, circuit simulators
- **Pros**: Simpler interaction, no drag collision issues, easier to implement
- **Cons**: Two-step process (less intuitive), accidental clicks
- **Effort**: Small-Medium (1-2 days - click handlers, line rendering)

**Option C: Drag-to-Connect (Minimal)**
- Visual: SVG lines
- Interaction: Drag from output slot, drop on input slot (no rerouting)
- **Pros**: Intuitive, single gesture
- **Cons**: Requires collision detection, dnd-kit may not support well (two concurrent drag contexts)
- **Effort**: Medium (2-3 days - custom drag handling, line rendering)

**RECOMMENDATION**: **Option B (Click-to-Connect)** for Phase 3, with Option A as Phase 5+ enhancement.

**Rationale**:
1. **Fastest path to working connections**: Phase 1-2 took longer than expected (95% complete but no connections). Option B gets connections working in 1-2 days.
2. **Derisks dnd-kit constraints**: dnd-kit is already handling block drag (library → lane). Adding slot-to-slot drag may conflict. Click-to-connect sidesteps this.
3. **Good enough for prototyping**: Click-to-connect is sufficient for 3-10 block patches (Phase 3-4 scope). Complex patches (20+ blocks) benefit more from drag-to-connect, but that's Phase 5+ concern.
4. **Upgrade path clear**: Once click-to-connect works, can add drag-to-connect as alternative interaction (user preference toggle).

**Implementation Details**:
- Store adds `pendingConnection: { fromBlock, fromSlot } | null` observable
- Click output slot → sets pendingConnection, highlights valid input targets (green glow)
- Click valid input → calls `store.connect()`, clears pendingConnection
- Click elsewhere → clears pendingConnection (cancel)
- Render connections as SVG `<path>` with quadratic bezier (start/end at slot centers, control point offset for curve)

#### Acceptance Criteria
- [ ] User clicks output slot, valid inputs highlight (green border)
- [ ] User clicks valid input, connection appears as SVG line
- [ ] User clicks invalid input, nothing happens (or error tooltip)
- [ ] User clicks empty space, pending connection cancels (highlights clear)
- [ ] Connection lines render as smooth curves (not straight lines)
- [ ] Multiple connections from same output supported
- [ ] Connection deletion works (click connection line, press Delete or click X button)

#### Technical Notes
- Use MobX observable for `pendingConnection` (Inspector can show "Connecting from: RadialOrigin.origin" status)
- SVG path formula: `M x1,y1 Q cx,cy x2,y2` where `cx = (x1+x2)/2`, `cy = y1` (horizontal curve)
- Color connections by type (Field = blue, Signal = green, Event = yellow)
- Add `data-connection-id` to path for click detection

### P0: Compiler Architecture

**Status**: Not Started
**Complexity**: Large (architectural decision)
**Dependencies**: Connection UI (need wired graph to compile)
**Spec Reference**: PROJECT_SPEC.md § 2 Architecture § Compiler
**Status Reference**: STATUS-2025-12-12-180205.md § Ambiguities § Question 2

#### Description

Phase 4 requires compiling patch JSON (graph of blocks + connections) into executable V4 `Program<RenderTree>`. The compilation strategy determines code structure, performance, and debugging experience.

**Evidence from STATUS**: `BlockBehavior.compile` stub exists in blocks.ts, but no semantics defined. No compiler.ts file exists.

#### Analysis & Recommendation

**Option A: Block Methods (OOP Approach)**
- Architecture: Each block has `compile(inputs: Signal[]) => Signal<Output>` method
- Compiler walks graph, calls `block.compile()` with upstream results, wires closures
- **Pros**: Decentralized (blocks self-contained), familiar OOP pattern
- **Cons**: Hard to optimize (no global view), closures don't serialize (can't export compiled code)
- **Effort**: Medium (2-3 days - block compile methods, graph walker)

**Option B: AST + Interpreter**
- Architecture: Compiler builds AST (expression tree), interpreter evaluates at runtime
- AST nodes: `FieldNode`, `SignalNode`, `MapNode`, `ScanNode`, etc.
- **Pros**: Can optimize (constant folding, dead code elimination), AST serializable
- **Cons**: Interpreter complexity, performance overhead, large design surface
- **Effort**: Large (5-7 days - AST types, interpreter, optimizations)

**Option C: Direct Function Generation (Pragmatic)**
- Architecture: Compiler directly produces V4 kernel calls (Signal.map, scan, etc.)
- Each block definition has `emitV4(inputs) => V4.Signal` factory
- Result: Closures that V4 kernel executes
- **Pros**: Simple, fast runtime, leverages V4 kernel, small surface area
- **Cons**: Closures don't serialize (but patch JSON does), debugging harder (no AST to inspect)
- **Effort**: Medium (3-4 days - block emit functions, topological walk, V4 integration)

**RECOMMENDATION**: **Option C (Direct Function Generation)** for Phase 4-5.

**Rationale**:
1. **Matches V4 kernel design**: V4 is already pull-based with Signal/Event primitives. Compiler just needs to wire them together.
2. **Fast runtime**: V4 kernel is optimized. Generated closures execute at native speed.
3. **Simpler than AST**: No need to design expression language. Block emitters are straightforward: `RadialOrigin.emit` returns `V4.Field.radial(params)`.
4. **Serialization solved at patch level**: Patch JSON is serializable. Compilation happens on load (acceptable for editor use case).
5. **Good enough for 3-10 archetypes**: Not building a production compiler. Editor compiles patches client-side, performance not critical.

**Implementation Details**:
- Compiler algorithm:
  1. Topological sort of block graph (Render → Scene, detect cycles)
  2. For each block (reverse topo order):
     - Lookup `BlockBehavior` from registry
     - Call `behavior.emit(inputs)` with upstream V4 primitives
     - Store result in `Map<BlockId, V4.Signal | V4.Event | V4.Field>`
  3. Return Render block's output as `Program<RenderTree>`
- Block emit signature: `emit(inputs: V4Inputs, params: BlockParams, ctx: CompileContext) => V4.Output`
- `CompileContext` provides: seed, scene data, viewport

**Alternative for Phase 6+**: If users want to export compiled code (not just patch JSON), add code generation layer: `compile(patch) => TypeScript source`. This is optional enhancement.

#### Acceptance Criteria
- [ ] Compiler produces working V4 Program for simple patch (Scene → Fields → Render)
- [ ] Topological sort detects cycles (error: "Cycle detected: Block A → B → A")
- [ ] Missing connections handled gracefully (error: "Block X input 'foo' not connected")
- [ ] Compilation errors show block location ("Error in Block 'RadialOrigin' (ID: block-5)")
- [ ] Compiled program runs at 60fps for particle animation (100 particles)
- [ ] Recompilation on param change completes in <50ms (debounced)

#### Technical Notes
- Use depth-first search for topo sort (standard algorithm, 20 lines)
- Cycle detection: track visited + recursion stack
- Default inputs: If slot optional, use safe default (e.g., Field<number> defaults to `() => 0`)
- Compiler memoization (Phase 5+): Cache block outputs, recompile only changed subgraph

### P1: Auto-Compile Behavior

**Status**: Not Started
**Complexity**: Small (config decision + debounce)
**Dependencies**: Compiler (need working compiler first)
**Spec Reference**: PROJECT_SPEC.md § Open Questions § Q4
**Status Reference**: STATUS-2025-12-12-180205.md § Ambiguities § Question 3

#### Description

When user changes a parameter, adds a block, or creates a connection, should the preview update automatically or require manual compile trigger?

**Evidence from STATUS**: PROJECT_SPEC says "auto-compile with 200ms debounce" but no implementation exists. Transport.tsx has stub "TODO Phase 2: Implement playback (RAF loop)".

#### Analysis & Recommendation

**Option A: Auto-Compile (Eager)**
- Trigger: MobX autorun on any graph/param change
- UX: Instant preview update (feels magical)
- **Pros**: Best UX for exploration (tweak and see)
- **Cons**: Performance (recompile on every slider drag?), battery drain
- **Effort**: Small (add autorun, risk of lag)

**Option B: Auto-Compile with Debounce (PROJECT_SPEC recommendation)**
- Trigger: MobX autorun + 200ms debounce
- UX: Preview updates ~200ms after last change (balance speed/performance)
- **Pros**: Balances responsiveness and performance, prevents compile spam
- **Cons**: Still recompiles frequently, complex patches may lag
- **Effort**: Small (add autorun + debounce utility)

**Option C: Manual Compile**
- Trigger: User clicks "Compile" button in Transport
- UX: Explicit control, predictable performance
- **Pros**: User controls performance, no surprise lag, good for complex patches
- **Cons**: Extra click, less immediate feedback
- **Effort**: Trivial (button + click handler)

**RECOMMENDATION**: **Option C (Manual Compile)** for Phase 4, upgrade to Option B in Phase 5.

**Rationale**:
1. **Derisk Phase 4**: First-time compiler integration has unknown performance. Manual compile lets us measure before adding auto-compile.
2. **Simpler to implement**: Button + click handler is 5 lines. Debounced autorun is 30 lines + potential edge cases (dispose, re-trigger, etc.).
3. **Good for testing**: Manual compile makes it easy to verify compilation correctness (change param, compile, check output vs auto-compile which may mask bugs).
4. **User can always click**: For Phase 4 scope (3-10 blocks), clicking "Compile" after tweaks is acceptable. Once we know performance is good, add auto-compile in Phase 5.

**Upgrade Path (Phase 5)**:
- Add toggle in Transport: "Auto-compile" checkbox (default: off)
- When enabled, add MobX reaction:
  ```typescript
  reaction(
    () => [store.blocks, store.connections, store.selectedBlock?.params],
    () => debouncedCompile(),
    { delay: 200 }
  )
  ```
- Dispose reaction on unmount

#### Acceptance Criteria
- [ ] "Compile" button in Transport bar
- [ ] Click "Compile" triggers compilation, preview updates
- [ ] Compilation errors display in UI (toast or error panel)
- [ ] Compilation success shows indicator (green checkmark, "Compiled at HH:MM:SS")
- [ ] Button disabled while compiling (prevents double-compile)
- [ ] Phase 5: Auto-compile toggle works (checkbox on = auto, off = manual)

#### Technical Notes
- Store method: `compile() => { this.compiledProgram = compiler.compile(this) }`
- Error handling: Wrap compile in try/catch, set `this.compileError: string | null`
- Debounce utility: `const debouncedCompile = debounce(() => store.compile(), 200)`
- Dispose debounce on unmount (Phase 5)
