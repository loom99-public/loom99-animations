## Executive Summary

This sprint focuses on **clean implementation of the new architecture** by removing legacy systems rather than migrating them. With backward compatibility concerns removed, we can delete entire legacy codebases and implement the unified architecture from scratch.

The modular store system is already in place, providing a solid foundation. We will build directly on this foundation to implement the unified compiler and TimeCtx integration specified in the architecture.

## Deliverable 1: Legacy System Removal and Unified Compiler Foundation

**Priority**: P0 (Critical)
**Effort**: Large (1-2 weeks)
**Dependencies**: None

### Description
Remove all legacy compilation systems and implement the unified dependency graph compiler as specified in the architecture. This delivers the foundational compilation model that enforces architectural invariants.

This involves:
1. Deleting legacy compiler directories and files
2. Implementing the UnifiedCompiler class with dependency graph building
3. Adding cycle detection across system boundaries
4. Implementing bus compilation contract
5. Creating stable ordering enforcement
6. Integrating with the existing modular store system

### Acceptance Criteria
- [ ] Legacy `gallery/src/compiler/blocks/` directory completely deleted
- [ ] Legacy `portUtils.ts` file deleted (replaced by bus system)
- [ ] Legacy compilation context files deleted
- [ ] UnifiedCompiler class implemented with dependency graph building
- [ ] Graph builder handles both blocks and buses as nodes
- [ ] Cycle detection works across block-to-block and bus-to-block connections
- [ ] Bus compilation contract generates Signal evaluators and FieldExpr nodes
- [ ] State boundary validation prevents implicit state through closures
- [ ] Stable ordering enforcer ensures deterministic evaluation
- [ ] Compiler integrates with existing PatchStore and BusStore
- [ ] All existing tests pass with new compiler
- [ ] New architecture tests added and passing

### Technical Notes
- The modular store system (PatchStore, BusStore, etc.) is already implemented
- Bus system has complete type system, just needs compilation to evaluators
- Dependency graph should be built from patch state (blocks + connections + buses)
- Consider using topological sort for stable ordering
- Bus compilation needs to handle combine modes (sum, average, max, min, last, layer)
- FieldExpr nodes should be created for Field-world buses

## Deliverable 2: TimeCtx Integration and Runtime Pipeline

**Priority**: P0 (Critical)
**Effort**: Medium (3-5 days)
**Dependencies**: Deliverable 1 (Unified Compiler)

### Description
Implement the TimeCtx management system and update the runtime evaluation pipeline to use pull-based evaluation with proper TimeCtx propagation. This establishes the single source of truth for all temporal behavior.

This involves:
1. Creating TimeCtx manager with proper interface
2. Updating runtime to use pull-based evaluation pipeline
3. Integrating TimeCtx propagation through all evaluators
4. Implementing state block reconstruction with TimeCtx
5. Adding phase signal evaluation with proper time context
6. Creating TimeCtx factories for scrub vs performance modes

### Acceptance Criteria
- [ ] TimeCtx interface defined with t, dt, frame, and mode fields
- [ ] TimeCtxManager class implemented as single time source
- [ ] Runtime updated to use pull-based evaluation instead of push
- [ ] All signal evaluators receive TimeCtx parameter
- [ ] TimeCtx propagation works through entire evaluation chain
- [ ] State block reconstruction uses TimeCtx for deterministic behavior
- [ ] Phase signal evaluation respects TimeCtx mode (scrub vs performance)
- [ ] TimeCtx factories create appropriate contexts for different modes
- [ ] Frame counter enables proper stateful behavior
- [ ] Performance impact <5% from TimeCtx propagation
- [ ] Scrub behavior works correctly with TimeCtx

### Technical Notes
- TimeCtx should be immutable to prevent accidental mutation
- Pull-based evaluation means evaluating sinks first, then dependencies
- State blocks need TimeCtx for proper reconstruction during scrubbing
- Phase signals should use TimeCtx.t for temporal progression
- Mode field enables future optimizations for scrub vs performance
- Frame counter essential for deterministic stateful behavior

## Deliverable 3: Initial State Block Implementation

**Priority**: P1 (High)
**Effort**: Medium (3-5 days)
**Dependencies**: Deliverable 1 (Unified Compiler), Deliverable 2 (TimeCtx)

### Description
Implement the foundational state block types with explicit state management and scrub behavior. This delivers the stateful building blocks needed for phase clocks and user-defined state while maintaining architectural invariants.

This involves:
1. Defining StateShape and ScrubPolicy interfaces
2. Creating StateBlock interface extending regular Block
3. Implementing Delay block with configurable delay and scrub behavior
4. Implementing Integrate block with accumulation and reset modes
5. Implementing History block with configurable buffer size
6. Adding state block registration and lifecycle management
7. Creating state serialization/deserialization for save/load

### Acceptance Criteria
- [ ] StateShape interface defined for type-safe memory description
- [ ] ScrubPolicy enum with hold, reset, interpolate, recompute options
- [ ] StateBlock interface extends Block with state-specific properties
- [ ] State block registration system integrated with block registry
- [ ] Delay block implemented with time parameter and scrub policy
- [ ] Integrate block implemented with accumulation and configurable reset
- [ ] History block implemented with ring buffer and configurable depth
- [ ] State blocks compile through UnifiedCompiler with proper dependencies
- [ ] State reconstruction works correctly during scrubbing
- [ ] State serialization preserves all necessary information
- [ ] Memory usage is bounded and predictable for all state blocks
- [ ] State inspection shows current state values in UI

### Technical Notes
- StateShape should be serializable and type-safe
- ScrubPolicy determines behavior when time jumps (scrubbing)
- State blocks must declare dependencies for proper compilation order
- Use immutable state snapshots for scrub safety
- State initialization should be explicit and controllable
- Consider memory pooling for frequently created state blocks
