The following design decisions need answers from user:

### Question 1: Connection Rendering + Interaction
**Context**: Users need to wire blocks together (output slot → input slot)

**How it was guessed**: Punted to "Phase 3" with no concrete design

**Options**:
- **Option A**: SVG lines connecting blocks (like node editors: Blender, Unreal Blueprint)
  - Pros: Visual, familiar, shows data flow
  - Cons: Complex to implement (curved lines, collision detection, drag to reroute)
  - Implementation effort: Medium-Large (3-5 days)

- **Option B**: Click-to-connect (click output, then click input, line appears)
  - Pros: Simpler interaction, no drag collision issues
  - Cons: Less intuitive, two-step process
  - Implementation effort: Small-Medium (1-2 days)

- **Option C**: Drag from output to input (like Figma auto-layout wiring)
  - Pros: Intuitive, single gesture
  - Cons: Requires custom collision detection, dnd-kit may not support well
  - Implementation effort: Medium (2-3 days)

**Impact of wrong choice**: Could require full rewrite of connection UI if initial approach doesn't scale to 20+ blocks/50+ connections.

### Question 2: Compiler Design
**Context**: Phase 4 requires compiling patch JSON to executable V4 Program<RenderTree>

**How it was guessed**: `BlockBehavior.compile` stub exists, but no semantics defined

**Options**:
- **Option A**: Each block has `compile(inputs) => V4 function` method, compiler walks graph and wires closures
  - Pros: Decentralized, blocks self-contained
  - Cons: Hard to optimize, closures may not serialize

- **Option B**: Compiler builds AST, then interprets AST at runtime
  - Pros: Can optimize, can serialize AST
  - Cons: Interpreter complexity, performance overhead

- **Option C**: Compiler emits TypeScript code, evals it (like Svelte compiler)
  - Pros: Fast runtime, leverages V8 optimizer
  - Cons: Security (eval), debugging hard

**Impact of wrong choice**: Phase 4 could be blocked for weeks if compiler architecture is fundamentally wrong.

**Recommendation**: User should review V4 kernel compiler patterns (if any exist) and decide on compilation strategy before Phase 4 starts.

### Question 3: Auto-Compile Behavior
**Context**: When user changes a parameter, should preview update immediately?

**How it was guessed**: PROJECT_SPEC says "auto-compile with 200ms debounce" but no implementation exists

**Options**:
- **Option A**: Auto-compile on every graph change (MobX autorun)
  - Pros: Instant feedback, magical UX
  - Cons: Performance (recompile on every slider drag?)

- **Option B**: Auto-compile with debounce (PROJECT_SPEC recommendation)
  - Pros: Balance feedback speed and performance
  - Cons: Still recompiles frequently, may choke on complex patches

- **Option C**: Manual compile (user clicks "Compile" button)
  - Pros: User control, predictable performance
  - Cons: Worse UX, extra click

**Impact of wrong choice**: Could lead to janky UI (lag on param changes) or battery drain (constant recompilation).

**Recommendation**: Start with Option C (manual compile) for Phase 4, add auto-compile in Phase 5 if performance allows.
