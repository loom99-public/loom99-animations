## Executive Summary
Phase 1 establishes the foundational data model and store management for the bus-centric architecture. This sprint focuses on implementing the core Bus interface, updating existing types to support bus awareness, and adding basic bus management functionality to the EditorStore.

The scope is deliberately limited to data model and store changes only - no UI modifications or compiler updates are included. These will be addressed in subsequent phases.

Total work items: 7 (P0: 5, P1: 2)

## Backlog by Priority

### P0 (Critical) - Core Data Model

#### 1. Bus Interface and Type System
**Status**: Not Started
**Effort**: Medium (3-5 days)
**Dependencies**: None
**Spec Reference**: Transformation plan Phase 1 • **Status Reference**: Missing Components by Phase

**Description**:
Implement the core Bus interface and related types that form the foundation of the bus-centric architecture. This introduces the concept of typed buses that can collect and distribute values throughout the patch.

**Acceptance Criteria**:
- [ ] Bus interface defined with id, name, type, combineMode, and defaultValue properties
- [ ] BusCombineMode type exported with 6 standard modes: 'sum' | 'average' | 'max' | 'min' | 'last' | 'layer'
- [ ] BusConnectionTracker interface for monitoring publisher/subscriber relationships
- [ ] All types exported from types.ts for reuse across editor modules
- [ ] JSDoc documentation for all bus-related interfaces explaining their role

**Technical Notes**:
- Place Bus interface before Patch interface in types.ts for logical ordering
- Use string type for bus.id to maintain consistency with BlockId and LaneId patterns
- combineMode defaults should be defined as constants for easy reference
- BusConnectionTracker is preparatory for Phase 2 compiler work but needed now for completeness

#### 2. Slot Interface Bus Awareness
**Status**: Not Started
**Effort**: Small (1-2 days)
**Dependencies**: Bus interface defined
**Spec Reference**: Slot updates in Phase 1 • **Status Reference**: Current Architecture State

**Description**:
Update the Slot interface to include optional bus binding properties. This enables slots to declare their intention to publish to or subscribe from specific buses without breaking existing wire-based connections.

**Acceptance Criteria**:
- [ ] Slot interface extended with optional publishesToBusId?: string property
- [ ] Slot interface extended with optional subscribesToBusId?: string property
- [ ] Slot interface extended with optional adapterChain?: any[] property for future type conversion
- [ ] All properties are optional to maintain backward compatibility
- [ ] Existing slot creation points continue to work without modification

**Technical Notes**:
- Making properties optional ensures smooth transition from wire-only to hybrid approach
- adapterChain placeholder for Phase 2 implementation but needed for type completeness
- Consider adding validation functions later to prevent conflicting bus/wire assignments

#### 3. Patch Structure Bus Integration
**Status**: Not Started
**Effort**: Small (1-2 days)
**Dependencies**: Bus interface, Slot bus awareness
**Spec Reference**: Patch updates in Phase 1 • **Status Reference**: Existing Data Model

**Description**:
Update the Patch interface to include an array of Bus objects and modify version handling to distinguish between wire-based and bus-based patches.

**Acceptance Criteria**:
- [ ] Patch interface includes buses: Bus[] array
- [ ] Patch.version type changed from number to string supporting '1.0' and '2.0-bus' formats
- [ ] toJSON() in EditorStore returns buses array (empty for legacy patches)
- [ ] loadPatch() handles both legacy (version: number) and bus-aware patches
- [ ] Migration logic to convert legacy patches to bus-aware format with empty buses array

**Technical Notes**:
- Version string approach allows graceful degradation for patches without buses
- Keep connections[] array for backward compatibility during transition period
- Empty buses array on new patches provides consistent structure

#### 5. Basic Bus CRUD Operations
**Status**: Not Started
**Effort**: Medium (3-5 days)
**Dependencies**: EditorStore bus state
**Spec Reference**: Bus management actions in Phase 1 • **Status Reference**: Missing Components by Phase

**Description**:
Implement core bus management actions for creating, updating, and deleting buses within the EditorStore.

**Acceptance Criteria**:
- [ ] createBus(type: SlotType, name?: string): string creates bus with unique ID and default settings
- [ ] deleteBus(busId: string): void removes bus and clears slot references
- [ ] updateBus(busId: string, updates: Partial<Bus>): void modifies bus properties
- [ ] validateBusType(busType: SlotType): boolean ensures only valid slot types become buses
- [ ] Default naming convention: "Bus [Type]" or custom name if provided
- [ ] ID generation follows existing nextId pattern

**Technical Notes**:
- createBus should return bus ID for immediate use in slot binding
- deleteBus must clean up publishesToBusId/subscribesToBusId references in all blocks
- validateBusType prevents invalid bus types (e.g., 'Program' as bus type)
- Consider bus name uniqueness validation within a patch

### P1 (High) - Bus Connection Management

#### 6. Slot-to-Bus Binding Methods
**Status**: Not Started
**Effort**: Medium (3-5 days)
**Dependencies**: Basic CRUD operations
**Spec Reference**: Implementation recommendations Phase 1 • **Status Reference**: Current Architecture State

**Description**:
Add methods to bind and unbind slots from buses, updating slot properties and managing bus subscription tracking.

**Acceptance Criteria**:
- [ ] publishSlotToBus(blockId: BlockId, slotId: string, busId: string): void sets publishesToBusId
- [ ] subscribeSlotToBus(blockId: BlockId, slotId: string, busId: string): void sets subscribesToBusId
- [ ] unpublishSlotFromBus(blockId: BlockId, slotId: string): void clears publishesToBusId
- [ ] unsubscribeSlotFromBus(blockId: BlockId, slotId: string): void clears subscribesToBusId
- [ ] Validation to prevent slot from publishing/subscribing to multiple buses
- [ ] Validation to ensure slot type matches bus type

**Technical Notes**:
- Methods should be MobX actions for proper reactivity
- Include type checking: slot.type must match bus.type for valid binding
- Consider whether to allow a slot to both publish to one bus AND subscribe to another
- Clear any conflicting wire connections when binding to bus (Phase 2 consideration)

#### 7. Bus Discovery and Inspection
**Status**: Not Started
**Effort**: Small (1-2 days)
**Dependencies**: Slot binding methods
**Spec Reference**: None (quality of life improvement)

**Description**:
Add utility methods to inspect bus relationships and discover publishers/subscribers for debugging and future UI implementation.

**Acceptance Criteria**:
- [ ] getBusPublishers(busId: string): Array<{blockId, slotId}> returns all slots publishing to bus
- [ ] getBusSubscribers(busId: string): Array<{blockId, slotId}> returns all slots subscribing from bus
- [ ] getSlotBusBinding(blockId: BlockId, slotId: string): {publishesTo?: string, subscribesTo?: string}
- [ ] findBusesBySlotType(slotType: SlotType): Bus[] returns all buses compatible with slot type
- [ ] isBusBound(busId: string): boolean indicates if bus has any publishers or subscribers

**Technical Notes**:
- These are computed properties for reactive updates
- Return arrays should be immutable (use .filter() on observable arrays)
- Useful for Phase 3 UI implementation and debugging bus connections
