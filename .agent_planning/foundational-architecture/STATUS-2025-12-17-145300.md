## Executive Summary
Overall: 30% complete | Critical issues: 9 | Tests reliable: partial

The current implementation has a solid V4 functional animation foundation but is missing most of the core architectural components described in the Foundational Architecture specification. The system has working animations and a visual editor, but they operate on different time models and lack the unified "pure function of (TimeCtx, Patch Definition, Explicit State)" invariant.

## Current Implementation State

### 1. Single Invariant - NOT IMPLEMENTED
**Spec**: System is pure function of (TimeCtx, Patch Definition, Explicit State)
**Current**: Mixed time models and implicit state

Issues:
- V4 animations use `Signal<A> = (t: Time, ctx: Context) => A` - close but missing TimeCtx structure
- Editor/player uses `Program<T>.signal: (tMs: number, rt: RuntimeCtx) => T` - different signature
- No unified TimeCtx with mode (scrub vs performance)
- Time is not treated as data throughout the system

### 2. Canonical Evaluation Pipeline - PARTIALLY IMPLEMENTED
**Spec**: TimeCtx → Signals → Fields → RenderTree → Render
**Current**: Runtime evaluates signals directly to RenderTree

What exists:
- Signal evaluation in V4 core
- RenderTree production and rendering
- Lazy evaluation through signals

What's missing:
- TimeCtx as the single time source
- Fields as lazy expression graphs (Fields are compile-time only)
- Bus-based signal evaluation
- Separation of scrub vs performance modes

### 3. Time as Data - NOT IMPLEMENTED
**Spec**: TimeCtx with t, dt, frame, mode
**Current**: Simple time values

Current time handling:
- V4: `type Time = number` (wall clock seconds)
- Player: `tMs: number` (milliseconds)
- No `dt` (delta time) tracking
- No frame counter
- No mode distinction between scrub and performance

### 4. Signals as Pure Evaluators - PARTIALLY IMPLEMENTED
**Spec**: (TimeCtx, EvalCtx) → Value, evaluated once per frame, memoized
**Current**: Close but missing TimeCtx and memoization

V4 Signal implementation:
```typescript
type Signal<A> = (t: Time, ctx: Context) => A
```

Issues:
- Context contains Env+Input, not TimeCtx+EvalCtx
- No per-frame memoization
- No explicit EvalCtx separation

### 5. Phase Clocks - PARTIALLY IMPLEMENTED
**Spec**: Two forms - derived (stateless) and stateful (explicit memory)
**Current**: Only derived phase machines exist

What exists:
- PhaseMachine block with entrance/hold/exit phases
- Phase calculation based on absolute time
- `PhaseMachines.sample(pm, t)` for derived evaluation

What's missing:
- Stateful phase clocks (PhaseAccumulator, Integrate+Wrap)
- Scrub behavior declaration for stateful clocks
- Memory boundary enforcement
- Explicit state blocks for phase

### 6. Buses as First-Class Compilation Nodes - IN PROCOMPLETE
**Spec**: Buses compile to Signal/Field evaluators, shared reduction points
**Current**: Buses exist but compilation is incomplete

Bus implementation status:
- BusStore manages buses, publishers, listeners
- Bus compilation logic exists in `compiler/integration.ts`
- Missing: domain-specific reducers, adapter chains, stable ordering
- Missing: Bus compilation to unified evaluators

### 7. Fields as Lazy Expression Graphs - NOT IMPLEMENTED
**Spec**: FieldExpr DAGs evaluated in dense batches at sinks
**Current**: Fields are compile-time bulk arrays only

Current Field implementation:
```typescript
type Field<A> = (seed: Seed, n: number, ctx: CompileCtx) => readonly A[]
```

Issues:
- No runtime Field evaluation
- No expression graph representation
- No lazy evaluation at sinks
- Fields evaluated once at compile time, not queried on demand

### 8. Element Identity - PARTIALLY IMPLEMENTED
**Spec**: Domain with stable element IDs, consistent ordering
**Current**: Basic element handling but no Domain concept

What exists:
- Per-element arrays in Fields
- Element IDs in some contexts
- Basic grouping in animations

What's missing:
- Domain parameterization of Field evaluation
- Explicit topology (neighbors)
- Stable identity across compilation
- Domain mismatch validation

### 9. State as Explicit and Scoped - MINIMAL
**Spec**: State only in Delay, Integrate, History, Explicit state blocks
**Current**: No explicit state blocks

Current state handling:
- Player maintains time and playback state
- No user-facing state blocks
- No state declaration or scrub policies
- State is implicit in the player

### 10. Compiler vs Runtime Separation - PARTIALLY IMPLEMENTED
**Spec**: Compiler builds dependency graph, Runtime holds state and calls evaluators
**Current**: Clear separation exists but responsibilities are incomplete

Compiler responsibilities (partially implemented):
- Dependency graph building ✓
- Topological sort ✓
- Block compilation ✓
- Missing: cycle detection, memory boundary enforcement, stable ordering

Runtime responsibilities (partially implemented):
- Holds current state buffers ✓
- Calls evaluators ✓
- Missing: minimal design (knows too much), explicit state handling

## Major Architectural Gaps

### 1. Time Model Unification (CRITICAL)
The system has three different time representations:
- V4 Signal: `(t: Time, ctx: Context) => A`
- Player/Program: `(tMs: number, rt: RuntimeCtx) => T`
- Specification: `(TimeCtx, EvalCtx) => Value`

This breaks the single invariant and prevents proper scrub/performance mode separation.

### 2. Missing TimeCtx Structure (CRITICAL)
No TimeCtx with:
- `t`: absolute time
- `dt`: delta since last frame
- `frame`: monotonic counter
- `mode`: scrub | performance

### 3. No Explicit State Blocks (CRITICAL)
Cannot implement stateful phase clocks or user-defined state. Missing:
- Delay blocks
- Integrate blocks
- History blocks
- Explicit state declarations with memory shapes and scrub policies

### 4. Incomplete Bus Compilation (HIGH)
Buses exist but don't compile to proper evaluators with:
- Domain-specific reducers
- Adapter chains
- Stable ordering by sortKey
- Deterministic combination

### 5. No Runtime Field Evaluation (HIGH)
Fields are compile-time only. Missing:
- FieldExpr DAG representation
- Lazy evaluation at sinks
- Domain-aware evaluation
- Per-element closure avoidance

## Ambiguities in Specification

### 1. EvalCtx vs RuntimeCtx (HIGH)
**Question**: What is the relationship between EvalCtx (for signal evaluation) and RuntimeCtx (for program evaluation)?
**Current confusion**: Compiler types define RuntimeCtx, but specification uses EvalCtx
**Impact**: Unclear how to structure signal evaluation context

### 2. State Block Interface (MEDIUM)
**Question**: How do explicit state blocks declare their memory shape and scrub policy?
**Missing**: Interface specification for state block registration
**Impact**: Cannot implement stateful phase clocks or user state

### 3. FieldExpr Representation (MEDIUM)
**Question**: What is the structure of FieldExpr DAGs?
**Missing**: Concrete type definitions for expression graph nodes
**Impact**: Cannot implement runtime field evaluation

### 4. Bus Domain-Specific Reducers (MEDIUM)
**Question**: What are the reducer functions for each bus domain?
**Missing**: Specification of combination logic per domain
**Impact**: Buses cannot compile to meaningful evaluators

## Dependencies and Risks

### High Risk Areas
1. **Time Model Migration**: Changing signal signatures would break all V4 animations
2. **State Block Integration**: Integrating explicit state with current compiler
3. **Bus Compilation Completion**: Major architectural work
4. **Field Runtime Evaluation**: Changes fundamental compilation model

### Dependencies
1. Must resolve time model unification before implementing state blocks
2. Bus completion depends on domain-specific reducer specifications
3. Field runtime depends on FieldExpr type definitions
4. Phase clocks require explicit state blocks to be fully implemented
